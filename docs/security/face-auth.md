# Omarchy 红外人脸认证：锁屏自动刷脸，唤醒重试，sudo 人脸优先

> 核对日期：2026-09-20。状态：人脸比对、锁屏、显示器亮屏重试、sudo 与 Polkit 已验证；真正睡眠恢复及完整负向验收待实测。本文面向在新 Omarchy 环境实施配置的 Agent。

## 问题与目标

在 Omarchy 上，安装人脸识别软件只是第一步。红外补光是否工作、锁屏是否启动后台认证、睡眠后是否会重新扫描，以及 sudo 能否回退到密码，都需要一并实现。

本文以 ThinkPad X1 Carbon Gen 9 的实践为例，说明各组件应如何配置和修改。它专门针对 Omarchy，不扩展讨论其它 Linux 桌面的部署。硬件适配参数以目标电脑为准，Agent 根据现场版本编写必要实现；本文不附固定源码，也不依赖作者的配置备份。

起点是一套可正常登录、使用密码授权的 Omarchy 桌面。先阅读仓库 [AGENTS.md](../../AGENTS.md) 和环境提供的 omarchy 技能，个人定制放在用户目录，不修改 `/usr/share/omarchy/`。

### 最终应该是什么体验

我们希望人脸识别成为现有认证体系中的一个入口，并保留可靠的密码回退。

| 场景 | 需要实现的行为 |
| --- | --- |
| 锁屏 | 自动开始人脸识别；用户也能直接输入密码 |
| 人脸未匹配 | 正常结束本轮扫描；有指纹设备时可继续指纹认证 |
| 锁屏熄屏后亮屏 | 开始一轮新的识别 |
| 系统睡眠后唤醒 | 放弃睡眠前的扫描，设备恢复后重新识别 |
| 用户主动重试 | 提供明确的重试入口，例如锁屏空输入按 Enter |
| sudo / 图形提权 | 优先人脸，失败后按配置转指纹或密码 |
| 合盖、无摄像头或设备暂不可用 | 不阻塞正常的密码认证 |
| 认证取消或锁屏已解除 | 清理扫描进程和待执行的重试 |

具体认证顺序需要结合桌面能力确定。顺序执行的 PAM 链通常会先等待人脸，再等待指纹，最后进入密码；桌面若支持独立密码通道，则可以在后台扫描期间直接输入密码。Agent 应明确实际体验，不能把两种架构都描述为“密码随时可用”。

红外摄像头能改善低照度采集，但不能仅凭使用了红外，就断言系统具备经过验证的活体检测或与 Windows Hello 相同的安全能力。

## 环境与适用范围

| 项目 | 实测基线 |
|---|---|
| Omarchy / Hyprland | 4.0.4-1 / 0.56.2-2 |
| 锁屏 | Omarchy Shell，Quickshell 锁屏插件 |
| howdy-next / OpenCV | 3.4.0-1.1 本地补丁包 / 5.0.0-9 |
| 示例硬件 | ThinkPad X1 Carbon Gen 9，Chicony IR 摄像头 |

适用于希望为 Omarchy 配置红外人脸认证的电脑，不要求是同款 ThinkPad。前提是红外采集与补光能够在目标系统工作。没有可用 IR 摄像头时，不能将普通 RGB 认证称为本文的红外方案。不同 Omarchy 版本先核对锁屏实现与插件 API，不机械套用路径。

### 为什么选择这套识别引擎

示例采用 howdy-next。它使用 C++ 实现，通过 OpenCV DNN 运行 YuNet 人脸检测和 SFace 身份比对，再通过 PAM 参与认证。选择它的理由包括：减少 Python/dlib 绑定的维护环节、可以检查和修改识别源码，以及能够接入已有 Linux 认证流程。

这不是对所有项目进行全面评测后的唯一答案。Agent 在实施时应核对候选项目的当前维护情况、发行版支持、依赖兼容性、PAM 集成方式和已知问题。尤其要确认包名实际对应哪个项目、哪个分支，而不能把名称相近的 Howdy 实现视为同一套软件。

示例验证基线为 howdy-next 3.4.0 与 OpenCV 5。它使用 C++23，推理由 OpenCV DNN 完成。这些信息用于理解该实现，不要求其它环境采用相同版本，也不意味着另一个实现需要同样的依赖。

### 采集策略：尽量保持录入与认证一致

对于拥有可用 IR 通道的电脑，优先使用固定的红外采集通道，并在同一通道下录入用户模板。这样可以让模型面对较一致的图像来源。

Agent 需要确认设备实际输出的格式、分辨率、帧率和图像质量。除非需求确实要求多摄像头，否则不必增加自动切换 RGB 与 IR、按亮度改写全局配置等额外状态。如果确实需要多通道，应明确各通道的模板、并发访问和配置隔离策略。

### Omarchy 锁屏是系统接入的关键

实测基线的 Omarchy Shell 使用 Quickshell 锁屏，并将密码与后台生物认证分成两个 PAM 通道。人脸接入后台通道，唤醒重试由用户锁屏插件负责。Agent 应先读取当前安装版本的服务和插件源码，确认仍采用这套结构，再定向修改。

## Agent 执行前检查

完整实现可以按四层理解：

1. **硬件采集层**：定位 IR 摄像头，确认访问权限、采集格式和补光控制。
2. **识别层**：配置引擎、录入用户模板，在限定时间和资源内返回匹配结果。
3. **认证层**：把结果接入明确的 PAM 服务，保留原有账户规则与密码回退。
4. **交互与生命周期层**：在锁屏、亮屏、睡眠恢复及主动重试时启动认证，处理取消和竞争。

这也是推荐的实施顺序。先证明硬件和识别可以独立工作，再接入系统认证，最后处理锁屏事件。否则，一个“刷脸没反应”的现象可能同时涉及摄像头、权限、模型、PAM 和锁屏状态，难以定位。

需要先检查以下现场状态：

- Omarchy、Hyprland、Howdy、OpenCV 和指纹库的实际版本及来源。
- 正在运行的锁屏组件、实际使用的 PAM 服务、已有用户插件和重复启动入口。
- Howdy 是否已经安装或被本地修改；是否存在另一个 Howdy 实现、旧摄像头切换脚本或重复 PAM 条目。
- IR 图像接口、补光能力、活动会话的设备权限，以及已录入模板属于哪个用户和通道。
- sudo、Polkit、密码失败控制与指纹认证原本是否正常。

应形成一份实际修改清单。重复执行时，更新已存在的实现，不能重复添加 PAM 模块、监听进程、插件或配置键。用户路径遵循目标用户 HOME / XDG 配置，不能带入作者用户名。

## 备份

在当前电脑建立带时间戳的备份目录，并分别记录原本存在与不存在的文件。系统认证配置保存在 root-only 目录，例如 `/var/backups/omarchy-face-auth/<时间戳>/`；用户 shell 设置可保存在目标用户的数据目录中。由 Agent 根据现场权限创建目录，不要求复制固定备份命令。

备份范围包括将修改的 PAM 服务文件、已有 Howdy 配置、用户 shell 配置、已有锁屏插件，以及相关 systemd drop-in。记录安装包版本和服务原启用状态。人脸模板如需备份，保持私有，不提交仓库；全新环境由用户重新录入。

修改认证前保留可用的管理会话。后续只合并必要设置，不用示例覆盖整份文件。备份用途是恢复本轮改动，不能覆盖执行期间产生的其它用户修改。

## 配置步骤

### 1. 识别 IR 设备并实现补光

#### 找到真正的 IR 图像接口

Agent 应收集电脑型号、摄像头 USB 或总线标识、视频节点能力、稳定设备路径以及可用格式。一个摄像头可能暴露多个节点，其中一部分只输出元数据，并不能作为图像输入。

示例机器提供以下信息：

| 项目 | ThinkPad 示例的实际结果 |
| --- | --- |
| 电脑 | ThinkPad X1 Carbon Gen 9 |
| 摄像头 | Chicony，USB ID `04f2:b6ea` |
| RGB / IR | 分别拥有独立的图像接口 |
| IR 格式 | GREY，640×360，支持 15 FPS |
| 稳定路径 | 通过 `/dev/v4l/by-path/` 定位到 IR 接口 |
| 指纹 | Synaptics，USB ID `06cb:00fc` |

视频节点编号可能变化，因此实现应选择经过确认的稳定标识。即使是同型号电脑，也需要重新核对设备，不能凭示例中的节点编号选择相机。

#### 将补光作为独立能力验证

能读取灰度图像，不等于红外发射器已经开启。Agent 应观察实际画面质量，并确认设备是否需要额外启用补光。

实现可以使用设备已有驱动、成熟的补光工具，或针对已知硬件编写最小控制程序。选择的依据是目标设备支持情况，而不是强制所有机器采用同一种 helper。

若需要自行实现控制程序，它应满足以下要求：

- 只操作经过确认的目标设备与已知控制项。
- 在写入前检查控制能力、数据长度和允许范围。
- 需要修改时才写入，并读取结果确认设置生效。
- 操作可重复执行，失败应明确返回，不导致认证无限等待。
- 权限按照实际调用身份设计，优先使用现有设备访问机制，不随意增加 SUID 或开放全局写权限。

示例 Chicony 摄像头的实测控制为 UVC unit 13、selector 14，数据长度两字节；启用值为 `[2, 25]`，预期最大值为 `[2, 100]`。**这些是该设备的适配结果，不是通用红外控制参数。** 另一台电脑需要重新识别控制协议，不能以试写这些值代替适配。

补光应在扫描前处于可用状态。对于睡眠后会丢失设置的设备，需要在新的扫描前重新应用。扫描结束后的发射器状态、关闭策略以及是否影响其它摄像头应用，也应结合驱动行为进行验证。

### 2. 安装识别引擎，完成独立比对

先通过 Omarchy 支持的包管理入口检查并安装 `howdy-next`，核对其 AUR 配方与 [howdy-next 上游](https://codeberg.org/nathawat/howdy-next) 的来源。依赖由包配方解析，避免混用源码直装与包管理文件。若需要本文的推理修复，以经过审阅的源码构建本地包并记录补丁。

软件包、构建工具及依赖不是文章附件。Agent 应固定所采用的 release 或 commit，验证配方中的源文件校验；模型使用该版本提供的下载机制，并记录文件名、来源和校验值。移动分支上的同名文件不能当作已验证版本。

本机模型为 YuNet `face_detection_yunet_2026may.onnx` 与 SFace `face_recognition_sface_2021dec_int8.onnx`，存放于 `/usr/share/howdy/models/`；配置为 `/etc/howdy/config.ini`，个人模板为 `/etc/howdy/models/`。以目标包实际路径为准。先保持人脸 PAM 入口禁用，独立比对成功后才启用。

#### 配置图像与模型

Agent 应根据选定引擎的实际配置接口，设置设备、采集尺寸、帧率、扫描时长以及必要的图像预处理。配置项名称和命令语法应以安装版本为准。

示例使用的主要参数如下，供理解取值关系：

| 参数 | 示例取值 | 含义 |
| --- | --- | --- |
| IR 采集尺寸 | 640×360 | 与设备支持的原始格式一致 |
| 采集帧率 | 15 FPS | 控制采集频率 |
| 扫描超时 | 5 秒 | 限制一次尝试的等待时间 |
| 处理高度上限 | 320 | 控制处理图像规模 |
| CLAHE | 启用，clip limit 1.25，tile grid 8 | 对示例 IR 画面进行局部对比度增强 |
| YuNet 检测阈值 | 0.6 | 判断画面中是否检测到人脸 |
| SFace 身份阈值 | cosine 0.6942 | 判断检测到的人脸是否为已录入用户 |

检测阈值与身份阈值承担不同职责。画面太暗、补光未开启或设备选错，不能靠不断放宽身份阈值解决。上述参数只在示例模型与设备组合中得到验证；更换模型或图像链路后，需要重新验证。

#### 控制推理的资源消耗

识别进程必须在其运行环境的资源预算内完成工作。示例实现限制了进程 CPU 时间，而 OpenCV 默认并行推理可能让多个线程累计消耗预算，在扫描的墙钟时间结束前触发 SIGXCPU。

对应的实现要求是：**在生产认证路径初始化推理后端之前，限制 OpenCV 的推理线程数。** 示例设置为单线程，保留了原有 CPU、文件描述符、地址空间和 core dump 限制。

Agent 应检查目标版本是否已有等效处理。确实需要修改时，应在源码中实现并通过发行版的包构建流程安装，使补丁可追踪、可重建。不要通过修改二进制机器码或取消整套资源限制来掩盖问题。减少摄像头 FPS 与限制推理线程数也不是同一件事。

这一要求针对示例的运行问题；其它引擎是否需要限制线程，必须由其实现和测量结果决定。

#### 现场录入，再独立验证

启用补光、确认图像之后，由目标用户现场录入 IR 模板。模板必须属于实际使用者，并按识别引擎要求保护存储权限。

在接入 PAM 之前，先调用引擎支持的独立测试或比较入口，至少完成多次本人匹配，同时检查无人、遮挡和未匹配时的行为。记录实际使用的设备、模型、模板用户、耗时和退出状态。

正常未匹配、扫描超时、设备打开失败和进程崩溃需要区分。Agent 不应把所有非零退出都描述为崩溃，也不能仅凭进程没有崩溃就宣告识别成功。

### 3. 接入 Omarchy 的三处认证入口

本机只在以下三个服务接入 Howdy。它们是 Agent 在相同 Omarchy 基线上的主要修改点：

| 文件 | 要实现的修改 |
|---|---|
| `/etc/pam.d/sudo` | 合盖检查后，补光 → 人脸 → 指纹 → 原有密码链 |
| `/etc/pam.d/polkit-1` | 同样采用人脸优先，保留原有账户及会话规则 |
| `/etc/pam.d/omarchy-lock-fingerprint` | 将后台通道扩展为补光 → 人脸 → 指纹 |
| `/etc/pam.d/omarchy-lock-password` | 保持独立密码通道与失败锁定规则，不添加人脸 |

不要向 `system-auth`、`system-local-login` 全局加入人脸，也不默认修改显示管理器、SSH 或磁盘解密流程。最后检查所有 Howdy 引用，只留下有意配置的入口。

#### 先读目标系统的认证结构

PAM 文件名、控制标志和包含关系因发行版而异。Agent 应先检查 sudo、图形授权和锁屏实际使用的服务，以及它们已有的密码、指纹和失败锁定规则。

修改前保存现场基线，并保留可用的管理会话。实施应局限于用户要求的服务，不应为了方便向全局认证栈加入人脸模块，从而意外改变 SSH、TTY 或其它登录流程。

#### 系统授权的目标顺序

对于支持此结构的系统，sudo 与图形授权可按以下顺序实现：

**环境检查 → 补光准备 → 人脸认证 → 可选指纹认证 → 原有密码认证。**

需要保证：

- 人脸成功可完成相应认证，但不能绕过原有账户访问规则。
- 补光失败或人脸未匹配，不应阻断密码回退。
- 没有指纹设备时，不留下无意义的指纹等待步骤。
- 合盖、远程会话等条件，按明确策略跳过不适用的生物认证。
- 保留原有 account、password、session 规则，以及密码失败计数与锁定控制。

若采用 PAM 的数字跳转控制，跳转数必须依据最终条目数计算。示例中合盖检测跳过补光、人脸和指纹三条；删去指纹或添加其它步骤后，这个数值就不能原样保留。

图形授权还有可能受到服务沙箱限制。Agent 需要检查实际运行 helper 的设备访问策略，只调整完成认证所需的权限。不要因为示例包存在某个设备放行项，就推断目标实现也必须开放该设备。

#### 锁屏应利用现有的独立密码通道

示例 Omarchy 锁屏分成两个 PAM 通道：一个处理密码，另一个处理后台生物认证。人脸接入后台通道，并在其后保留指纹；密码通道维持原有规则。

这一结构使用户无需等待整轮生物认证结束，就能输入密码解锁。若较新版 Omarchy 更换了锁屏架构，应先评估其支持的扩展方式，准确实现和说明回退体验，不能仅靠把多个模块放进同一条 PAM 链就声称实现了并行密码入口。

还要检查锁屏启动后台认证的条件。示例原组件根据“是否录入指纹”决定是否启动后台通道。因此，在类似组件中新增人脸后，Agent 必须明确选择：保留指纹前置条件，或者将启用条件扩展为支持人脸认证。对于只配人脸的机器，不能遗漏这一步。

### 4. 在用户锁屏插件中实现重试

识别引擎负责一次扫描，锁屏组件负责扫描何时开始、结束和重新开始。两者需要清晰分工。

#### 三类事件需要重新认证

**显示器重新亮起。** 如果锁屏仍然有效，应启动一轮新扫描。一次亮屏只触发一次，不能让随后每个鼠标移动都取消并重启认证。

**系统睡眠恢复。** 睡眠前取消旧扫描，恢复后等待旧认证退出和设备就绪，再启动新扫描。示例监听 systemd-logind 的 `PrepareForSleep` 信号；若较新版 Omarchy 调整了事件接口，应重新核对接入点。

**用户主动重试。** 示例将空输入 Enter 定义为重试人脸，非空输入仍提交密码。实现时要同时检查输入视图和认证 service，避免视图提前过滤空输入，也不能把空 Enter 当作一次失败的密码提交。

#### 正确处理取消与迟到结果

仅仅在事件回调中再次启动 PAM，可能造成并发扫描或旧结果干扰。Agent 应设计至少包含以下含义的状态：

- 当前是否处于有效锁屏状态。
- 是否正在睡眠或等待设备恢复。
- 是否有认证正在运行。
- 是否已请求取消并等待重启。
- 当前结果是否仍属于有效的认证尝试。

实现应满足这些不变量：

1. 同一后台通道不会同时运行多个扫描。
2. 在取消旧任务之前，先标记它的结果不再有效。
3. 旧任务退出前，不启动新任务。
4. 连续重试请求合并处理。
5. 取消后迟到的成功结果不能解锁。
6. 已解锁时取消全部待执行重试。
7. 生物认证重试不打断独立密码通道。

示例采用约 750ms 的重试延迟，并继续检查旧 PAM context 是否 inactive。延迟只用于平缓恢复过程，不能替代状态检查；另一台机器可能需要不同的设备就绪策略。

#### 按桌面的扩展机制安装修改

Omarchy 示例使用用户锁屏插件，保留原插件的认证能力声明与替代关系。由于认证 service 常驻，文件热更新不一定替换运行中的对象，因此需要在解锁状态重新启动 shell 并验证生效。

目标用户插件位于 `${XDG_CONFIG_HOME:-$HOME/.config}/omarchy/plugins/<插件 ID>/`。使用 Omarchy 的插件 clone 机制生成替代关系，修改锁屏 service 与输入视图，保留认证能力声明；通过 shell 配置确认只启用了目标插件。解锁后按该版本的 shell 重启方式加载，再查询锁屏运行状态和事件监听进程，确认运行的是新实现。

## 验收

安装成功不等于“摄像头亮了”，也不等于“某次比较返回成功”。Agent 应在目标环境完成以下验收，并区分真实硬件测试与模拟测试。

| 测试 | 应观察到的结果 | 示例实测 |
| --- | --- | --- |
| 独立本人比对 | 多次成功，匹配正确用户，无异常信号退出 | 已验证 |
| 无人、非本人、遮挡 | 不误认证；失败与超时正常结束 | 待完整验收 |
| sudo | 排除凭据缓存后，确认实际通过人脸授权 | 已验证 |
| 图形授权 | 操作成功，日志确认所用认证路径 | 已验证 |
| 正常锁屏 | 自动刷脸成功，密码入口可用 | 刷脸已验证；密码回退待实测 |
| 生物认证失败 | 按设计转指纹或密码，等待时间可接受 | 待实测 |
| 主动重试 | 开始新扫描，不产生空密码失败 | 状态机通过；手动操作待实测 |
| 熄屏再亮屏 | 只触发所需的新扫描 | 已验证 |
| 真正睡眠再唤醒 | 旧任务退出，设备恢复，新扫描可完成 | 状态机通过；实机待验证 |
| 取消与连续重试 | 不并发扫描，不接受迟到成功 | 状态机已验证 |
| 合盖、设备缺失 | 遵守跳过策略，密码仍可使用 | 待实测 |
| 暗光环境 | 验证实际补光与识别能力 | 全黑环境待实测 |

示例实现的独立 IR 比对约为 346–407ms，真实锁屏解锁约 568ms，sudo 和 Polkit 也观察到人脸认证成功。源码测试、锁屏状态机测试及显示器亮屏重试已经验证。这些数据说明方案具有实践基础，不是其它电脑的性能承诺。

示例记录尚未完成真正睡眠恢复、全黑环境、单独空 Enter 操作以及完整负向回退的实机验收。新环境实施时仍必须执行这些测试，不能继承示例的成功结论，也不能把状态机模拟测试当作硬件验收。

## 回滚

优先禁用 Howdy 认证，使用仍可用的密码或预留管理会话操作。禁用识别引擎不一定同时移除补光调用，需要完整回退时，定向恢复本轮修改的三个 PAM 服务，保留原有密码失败控制及后续用户修改。

在解锁状态停用新增用户锁屏插件，确认 clone 机制恢复原插件，再重启 shell。对本轮新建的补光程序与 systemd drop-in，先确认无剩余引用，再按变更清单移除；原本存在的文件恢复备份。服务配置发生变化时重新加载，并验收密码和原有指纹可用。

用户模板不作为常规回滚的删除对象，不清空整个配置目录，也不在锁屏期间强制重启 shell。

## 已知限制与维护

Agent 交付的应是可维护的安装结果，而不只是当场可用的配置。

识别引擎需要保留版本、构建方式和必要补丁的说明。桌面扩展应位于支持的用户配置位置。设备适配应记录硬件标识、控制协议和适用条件。所有权限调整都应能对应到实际需要访问设备的进程。

后续升级时，重点检查识别补丁是否仍需要、是否被覆盖，模型是否变化，PAM 基线是否更新，以及锁屏接口是否兼容。新版已有等效修复时，可以移除本地补丁，但仍需重新验证行为。

出现问题时，按“设备访问 → 补光 → 独立比对 → PAM → 锁屏事件”的顺序定位。恢复时应能禁用人脸入口并回到实施前的密码认证基线，不依赖删除整份 PAM 文件或关闭安全限制。

## 交给 Agent 的任务

完成实施后，应留下目标环境自身的记录：

- 实际硬件、软件版本与选择理由。
- 最终采用的采集设备、补光方式、模型和配置参数。
- 修改了哪些认证服务与桌面组件，每项修改实现什么行为。
- 按目标环境生成的源码、配置或构建产物，以及维护方式。
- 正向、负向、唤醒和回退测试结果，明确标出未验证项目。
- 可执行的禁用与恢复方法。

本文给出的是实现目标和工程约束。Agent 需要据此调查目标机器、生成适合该环境的代码，并用现场结果证明实现正确；不需要复刻示例电脑的目录结构、用户名、源文件或全部参数。
